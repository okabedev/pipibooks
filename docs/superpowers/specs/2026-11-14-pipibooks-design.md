# 피피북스(pipibooks) 설계서

- 작성일: 2026-11-14
- 상태: 승인 (2026-11-14)
- 이 문서는 승인 당시의 원본 기록이며 더 이상 고치지 않는다. 이후 기준 문서는 `docs/`의 주제별 문서다([목차](../../README.md)).

## 1. 의도

- 포트폴리오용 풀 스택 서비스다. 지인들에게 가볍게 소개해서 실제로 쓰게 하는 규모다.
- 보여 주려는 것은 백엔드 설계(멀티 모듈, 워커 분리, 외부 연동 모듈화)와 정리된 문서, Git 이력이다.
- 서비스를 24시간 운영할 필요는 없다. 서버가 꺼졌다 켜져도 문제없이 동작하는 것이 기준이다.

## 2. 목표 / 비목표 / 반목표

- **1차 목표:** 백엔드와 웹을 로컬 Docker로 실행하고 Cloudflare Tunnel을 통해 `pipibooks.com`으로 공개한다.
- **2차 목표:** React Native(Expo) 모바일 앱을 만든다. 스토어에는 출시하지 않는다.
- **비목표:** 대규모 트래픽 대응, 고가용성, 캐시와 메시지 큐, 소셜 기능(팔로우, 남의 책장 구경), 독서 상태 관리, 카카오 외 로그인.
- **반목표:** 규모에 비해 무거운 구조(기능별 모듈, 헥사고날), 정해진 시각에 반드시 실행되어야 하는 작업, 의미가 흐려지는 축약어.

## 3. 제품 정의

### 3.1 도서 정보
- **신간:** 워커가 국립중앙도서관 ISBN 서지 API에서 수집한 도서 중, 출판 예정일이 지난 30일 안에 있는 **이미 출간된** 책이다. 기간은 설정으로 바꿀 수 있다.
  - 수집 대상은 **종이책**만이다. ISBN 부가기호의 독자 대상 코드가 **학습참고서(5, 6)**인 책은 뺀다.
  - 처음 실행할 때는 실행 기록이 없으므로 30일 전부터 수집한다.
- **피피북스 TOP 100:** 전체 기간의 내부 평가로 계산한다. 평가 수를 보정한 평점 순으로 정렬한다.
  - 계산식: `score = (v/(v+m))·R + (m/(v+m))·C`
  - v는 그 책의 평가 수, R은 그 책의 평균 평점, C는 전체 평균 평점, m은 최소 평가 수(설정값, 기본 3)다.
  - 평가 수가 m 미만인 책은 순위에서 뺀다.
- **주간·월간 인기:** 기간 안에 새로 등록된 평가 수와 위시 추가 수를 더한 값 순이다. 기간은 최근 7일과 최근 30일이다.
  - 기간 안에 만들어졌고 **지금도 남아 있는** 평가와 위시만 센다. 이력 테이블은 두지 않는다.
  - 위시에 담은 책을 평가하면 위시 1개가 빠지고 평가 1개가 생기므로 점수는 그대로다. 사용자가 위시를 직접 지우면 그만큼 점수가 줄어든다.
- **카테고리별 도서:** KDC 2단계로 분류한다. 대분류는 10개이고, 그 아래 중분류가 있다.
  - 카테고리 화면은 두 탭으로 나뉜다. 하나는 그 분류 안에서만 계산한 보정 평점 순위이고, 다른 하나는 그 분류의 신간이다.
  - KDC 정보가 비어 있는 책은 ISBN 부가기호의 내용 분류(뒤 세 자리)로 분류를 정한다. 둘 다 없으면 미분류로 둔다.
  - 서점식 카테고리와 매핑표는 쓰지 않는다.
- 순위는 모두 내부 데이터만 쓴다. 외부 인기 데이터(도서관 정보나루 등)는 쓰지 않는다.
- 데이터가 부족해서 목록이 비면 "아직 평가가 부족해요" 같은 안내를 보여 준다.

### 3.2 도서 평가
- 평점은 0.5~5.0이며 0.5 단위다. 필수 항목이다.
- 코멘트는 선택 항목이며 최대 1000자다.
- 독서 기간은 선택 항목이다. 시작일과 종료일을 함께 입력하거나 함께 비워야 한다. 종료일은 시작일보다 앞설 수 없고, 미래 날짜는 입력할 수 없다.
- 한 사용자는 책 한 권에 평가를 하나만 남길 수 있다. 수정과 삭제가 가능하다.
- 평가한 책은 완독한 책으로 본다. 독서 상태(읽는 중, 읽음)는 다루지 않는다.
- 도서 상세 화면에서 다른 사람들의 평점과 코멘트를 닉네임과 함께 최신순으로 보여 준다. 페이지 단위로 나누어 불러온다.

### 3.3 나의 책장 (본인만 볼 수 있음)
- **위시 도서:** 추가하고 삭제할 수 있다. 이미 평가한 책은 위시에 담을 수 없다. 위시에 있던 책을 평가하면 위시에서 자동으로 빠진다.
- **평가한 책 목록:** 내가 평가한 책들을 모아서 보여 준다.
- **통계:**
  - 총 권수, 총 페이지 수, 평균 평점은 모든 평가를 대상으로 한다.
  - 연도별·월별 권수와 페이지 수는 독서 기간을 입력한 평가만 대상으로 하며, 독서 종료일을 기준으로 집계한다.
  - 페이지 수 정보가 없는 책은 페이지 통계에서 빠진다. 화면에 그 사실을 안내한다.

### 3.4 회원
- 카카오 로그인만 쓴다.
- 닉네임은 가입할 때 카카오 프로필 이름으로 채우고, 이후 직접 바꿀 수 있다. 닉네임은 중복될 수 있다.
- 회원 탈퇴를 지원한다. 탈퇴하면 그 회원의 평가와 위시를 삭제하고 카카오 연결을 끊는다.
- 도서 정보, 순위, 도서 상세(코멘트 포함)는 로그인하지 않아도 볼 수 있다. 평가, 위시, 책장은 로그인이 필요하다.

## 4. 검토한 접근 방식

### 4.1 인기 기준
- A: 모두 내부 평가 기반 ← **채택**
- B: TOP 100은 내부 평가, 주간·월간은 도서관 정보나루 대출 데이터
- C: 모두 외부 데이터
- 채택 이유: 사용자가 피피북스만의 순위를 원했다. 초기에 목록이 비는 문제는 안내 문구로 해결한다.

### 4.2 외부 API를 어디서 호출할지
- 처음에는 "외부 API 호출은 모두 워커가 맡는다"로 해석했다. 이 해석은 **철회했다.**
- 채택한 기준: 외부 API 클라이언트는 라이브러리다. 애플리케이션은 **작업의 성격**에 따라 나눈다.
  - 사용자 요청에 바로 응답해야 하는 작업(검색, 저장되지 않은 책의 상세 조회)은 API 서버가 직접 처리한다.
  - 오래 걸리거나 주기적으로 도는 작업은 워커가 처리한다.
- 검토했다가 버린 안:
  - API 서버가 워커의 내부 API를 거쳐 외부를 호출하는 방식: 워커가 꺼지면 검색도 멈춘다.
  - 미리 수집한 책만 검색하는 방식: 수집되지 않은 책은 찾을 수 없다.

### 4.3 백엔드 모듈 구성
- A: 역할별 모듈 ← **채택** (사용자가 이름과 배치를 조정함)
- B: 기능별 모듈. 기능 사이 의존성이 얽혀 있어서 이 규모에는 무겁다.
- C: 헥사고날. 단순한 데이터 조회와 저장이 대부분이라 과하다.

## 5. 아키텍처

### 5.1 레포 구조
```
pipibooks/
  clients/
    mobile/     ← React Native (Expo), 2차 목표
    web/        ← React
  services/     ← Gradle 멀티 모듈 루트
  infra/        ← Docker Compose, nginx, cloudflared, 백업 스크립트
  docs/
  .claude/skills/
  CLAUDE.md
```
- `services/app`과 `services/client`는 루트의 `clients/`와 이름이 비슷하다. 그래서 문서에서는 항상 경로로 부른다.

### 5.2 백엔드 모듈
```
services/
  app/
    api/      ← 실행 앱: REST API, 인증
    worker/   ← 실행 앱: 신간 수집, 데이터 보충, 순위 집계
  core/       ← 엔티티, 리포지토리, 비즈니스 로직
  client/     ← 외부 API 클라이언트 (nlk, kakao 패키지)
  support/    ← 공통 예외, 유틸리티
```
- **의존 방향:** `app/api`, `app/worker` → `core` → `client` → `support`. 그리고 `core` → `support`.
- `client`는 외부 응답을 자기만의 DTO로 돌려준다. `core`가 이를 도메인 객체로 바꾼다.
- 이 규모에서는 의존성 역전(`core`에 인터페이스를 두는 방식)을 쓰지 않는다.
- `core` 안은 기능별로 패키지를 나눈다: `book`, `review`, `wish`, `user`, `ranking`, `statistics`.
- 한 패키지에 클래스가 많아지면 하위 패키지로 나눈다.
- 데이터베이스 스키마는 하나이고, API 서버와 워커가 함께 쓴다.

### 5.3 도서 데이터
- 도서는 ISBN-13을 기준으로 식별한다.
- **저장 시점:** 사용자가 도서 상세를 처음 조회하거나, 평가하거나, 위시에 담을 때 저장한다. 워커가 신간을 수집할 때도 저장한다.
- **검색:** 국립중앙도서관 ISBN 서지 API를 먼저 쓴다.
  - 결과가 0건이거나 호출이 실패할 때만 카카오 도서 검색 API를 쓴다.
  - 결과는 ISBN-13 기준으로 중복을 없앤다. 페이지 나누기는 실제로 응답한 API의 방식을 따른다.
  - 외부 API 호출에는 짧은 타임아웃을 둔다. 두 API가 모두 실패하면 저장된 도서를 제목으로 간단히 찾는다(`LIKE`). 한국어 전문 검색은 넣지 않는다.
- **필드 병합:**
  - 서지 정보(페이지 수 포함)는 국립중앙도서관 데이터를 기본으로 쓴다.
  - 표지 이미지와 소개글이 비어 있으면 카카오 데이터로 채운다.
  - 카카오 API는 페이지 수를 주지 않는다.
- **API 키:** 국립중앙도서관 인증키, 카카오 REST API 키. 카카오 키는 로그인과 같은 앱의 키를 쓴다.

### 5.4 워커
- `@Scheduled`로 주기적으로 작업을 실행한다. 작업마다 실행 기록 테이블에 마지막 성공 시점을 남긴다.
- 워커가 켜질 때 실행 기록을 보고, 꺼져 있던 동안 놓친 구간을 따라잡는다.
- 작업 목록:
  - **신간 수집:** 하루 단위 구간으로 수집한다.
  - **데이터 보충:** 표지나 소개글이 비어 있는 도서를 카카오 데이터로 채운다.
  - **순위 집계:** TOP 100, 주간·월간 순위, 카테고리별 순위를 계산해서 순위 테이블에 저장한다.
- 워커는 단일 인스턴스로 실행한다. 분산 락은 쓰지 않는다.

### 5.5 인증 (모바일 확장 고려)
- 웹은 카카오 인가 코드를, 모바일은 카카오 SDK에서 받은 액세스 토큰을 API 서버로 보낸다.
- 서버는 카카오에 사용자 정보를 확인한 뒤 자체 JWT를 발급한다.
  - 액세스 토큰은 수명이 짧다.
  - 리프레시 토큰은 DB에 저장하고, 쓸 때마다 새 토큰으로 교체한다.
- 웹은 리프레시 토큰을 HttpOnly 쿠키로, 모바일은 보안 저장소로 보관한다. API 서버는 두 클라이언트를 같은 방식으로 처리한다.
- 카카오 Redirect URI는 로컬 주소와 `https://pipibooks.com`을 함께 등록한다.

### 5.6 인프라
- **로컬 개발:** Compose로 PostgreSQL만 띄우고, 애플리케이션은 IDE나 Gradle로 실행한다.
- **운영(1차 목표):** Compose 하나로 `postgres`, `api`, `worker`, `web`(nginx), `cloudflared`를 띄운다.
  - nginx는 `/`에서 웹 정적 파일을 제공하고, `/api`는 API 서버로 넘긴다. 도메인이 하나라서 CORS 설정이 필요 없다.
  - Cloudflare Tunnel은 토큰 방식(원격 관리 터널)을 쓰고, `pipibooks.com`을 `web:80`으로 연결한다.
- **비밀 값:** `.env` 파일로 관리하고 커밋하지 않는다. 대신 `.env.example`을 커밋한다.
- **백업:** `pg_dump` 스크립트를 `infra/`에 둔다.

## 6. 기술 스택

- **백엔드:** Java 25, Spring Boot 4.x(작업 시점의 최신 안정 버전), Gradle Kotlin DSL과 버전 카탈로그, PostgreSQL, Spring Data JPA, Flyway, springdoc OpenAPI.
  - 복잡한 집계는 JPQL이나 네이티브 쿼리로 작성하고, QueryDSL은 쓰지 않는다.
  - 테스트는 JUnit 5와 Testcontainers로 한다.
- **웹:** TypeScript, Vite, React Router, TanStack Query, Tailwind CSS. 모바일 화면에서도 쓸 수 있게 반응형으로 만든다.
- **모바일:** Expo(React Native)와 TypeScript. 카카오 네이티브 SDK를 쓰려면 Expo Go가 아니라 개발 빌드가 필요하다. 배포는 APK나 개발 빌드로 한다.
- **API 타입:** 각 클라이언트가 OpenAPI 문서에서 타입을 생성한다(openapi-typescript). 공유 패키지 폴더는 두지 않는다.

## 7. 규칙

### 7.1 코딩과 이름 짓기
- 가독성을 최우선한다. 의미를 흐리는 축약은 하지 않는다.
- **축약이 허용되는 경우:**
  - 고유 명사로 쓰이는 축약: ISBN, KDC, JWT, API 등
  - 긴 명칭: National Library of Korea → NLK
  - 3 단어 이상으로 이루어진 명칭
- 이 예외에 해당하는 축약어는 **사용자의 승인을 받은 뒤에만** 쓴다. 승인된 축약어는 `docs/decisions/`의 목록에 기록한다. 현재 승인된 것은 NLK 하나다.
- 식별자는 영어로 쓴다. 주석, 문서, 커밋 요약은 한국어로 쓴다.

### 7.2 문서
- `CLAUDE.md`는 200줄 이하로 쓰고, 규칙 요약과 문서 안내만 담는다.
- 나머지 문서는 한 파일에 한 주제만 담고 300줄 정도까지 쓴다. 길어지거나 따로 읽힐 주제가 섞이면 하위 문서로 나누고 링크한다.
- `docs/` 구성:
  - `README.md`: 목차
  - `product/`: 기능과 정책
  - `architecture/`: 구조
  - `conventions/`: 규칙
  - `decisions/`: 결정 기록과 승인된 축약어 목록
  - `roadmap/`: 로드맵과 마일스톤 파일
  - `superpowers/specs`, `superpowers/plans`: 설계서와 구현 계획
- 설계와 결정이 바뀌면 같은 PR 안에서 관련 문서도 함께 고친다.

### 7.3 Git
- GitHub 공개 레포 `pipibooks`를 원격 저장소로 쓴다.
- **브랜치(Git Flow):** `main`, `develop`, `feature/*`, `release/*`, `hotfix/*`.
  - 작업은 `feature/*` 브랜치에서 하고, PR을 만들어 `develop`에 병합한다.
  - 마일스톤이 끝나면 `release/*` 브랜치를 거쳐 `main`에 병합하고 태그를 단다. 태그는 마일스톤마다 `v0.N.0`이고, 1차 목표를 마치면 `v1.0.0`이다.
- **커밋:** Conventional Commits 형식이다. 예: `feat(api): 카카오 로그인 추가`.
  - scope는 `api`, `worker`, `core`, `client`, `support`, `web`, `mobile`, `infra`, `docs` 중 하나다.

## 8. 로드맵과 세션 인계

| 마일스톤 | 범위 |
|---|---|
| M0 설계 | `docs/` 구성, CLAUDE.md, 스킬, Git 레포와 브랜치 |
| M1 기반 | Gradle 멀티 모듈 뼈대, 웹 뼈대, 로컬 Compose(PostgreSQL), Flyway, 공통 오류 응답, 헬스 체크 |
| M2 인증 | 카카오 로그인, JWT, 회원·닉네임, 탈퇴 |
| M3 도서 | `services/client`(nlk, kakao), 검색, 도서 상세, 도서 저장·병합, KDC 분류 |
| M4 평가 | 평가 작성·수정·삭제, 도서 상세의 코멘트 목록 |
| M5 나의 책장 | 위시, 평가한 책 목록, 통계 |
| M6 워커 | 신간 수집, 데이터 보충, 순위 집계(카테고리 포함), 홈·카테고리 화면 |
| M7 배포 | 운영 Compose, nginx, Cloudflare Tunnel, 백업, `pipibooks.com` 공개 → 1차 목표 완료 |
| M8 모바일 기반 | Expo 개발 빌드, 카카오 로그인, API 연동 |
| M9 모바일 기능 | 홈, 검색, 상세, 평가, 책장 → 2차 목표 완료 |

- **마일스톤 파일:** `docs/roadmap/`에 마일스톤마다 하나씩 둔다. 각 파일에는 범위, 완료 기준, 상태(대기 / 진행 / 완료), 인계 메모를 적는다.
  - 인계 메모에는 진행 상황, 남은 작업, 진행 중에 내린 결정, 주의할 점을 적는다.
- **세션 흐름:**
  1. `pipibooks-milestone` 스킬로 마일스톤을 시작한다.
  2. `superpowers:writing-plans`로 구현 계획을 작성한다. 계획은 `docs/superpowers/plans/`에 저장한다.
  3. 계획을 실행한다.
  4. `pipibooks-milestone` 스킬로 마일스톤을 종료한다.
- **세션이 바뀔 때:** 새 세션은 CLAUDE.md의 안내에 따라 로드맵, 현재 마일스톤, 인계 메모 순으로 읽고 시작한다.
- **승인이 필요한 결정:** 진행 중에 생기면 작업을 멈추고 사용자에게 묻는다. 임시로 정하고 넘어가지 않는다. 승인을 받으면 `docs/decisions/`에 기록한다.
- **구현 계획 범위:** 이 설계서로는 M0 계획만 상세하게 작성한다. M1부터는 각 마일스톤을 시작할 때 계획을 쓴다.
- **미리 준비된 것:** 카카오 개발자 앱, 국립중앙도서관 인증키, Cloudflare의 `pipibooks.com` 도메인. GitHub 레포는 M0에서 만든다.
  - 키는 `.env`로만 다루고 문서나 커밋에 남기지 않는다.

## 9. 스킬

- **`pipibooks-milestone`** (`.claude/skills/`): 마일스톤을 시작, 재개, 종료하는 절차다.
  - 시작과 재개: 인계 메모를 확인하고 `feature/*` 브랜치를 만들거나 그 브랜치로 전환한다.
  - 종료: 완료 기준을 검증하고, 상태와 인계 메모를 갱신하고, PR과 릴리스를 진행한 뒤 다음 마일스톤을 안내한다.
- Git 규칙과 이름 짓기 규칙은 스킬로 만들지 않는다. `commit-commands`, `superpowers:finishing-a-development-branch`와 역할이 겹치기 때문이다.
  - 대신 `docs/conventions/`에 적고 CLAUDE.md에서 링크한다. 기존 스킬은 그 문서를 따른다.
- 구현 계획 작성과 실행은 superpowers 스킬을 그대로 쓴다.
